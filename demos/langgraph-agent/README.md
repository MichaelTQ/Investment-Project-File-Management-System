# 取证 Agent · LangGraph 实现

投资档案分拣系统里那个 agent 的 **LangGraph 版本**，独立可跑、不依赖主项目、不需要任何 API key。

主项目里这个 agent 现在是**手写的 tool-calling 循环**（OpenAI SDK）。第一版是 LangGraph 状态机，
因为整套分类架构被推翻而一起下线了（下线原因见主仓库 `docs/RETIRED_AGENT_ARCHITECTURE.md`：
关键词表覆盖 8/35 却卡在必经之路上）。这个目录把同一套边界用 LangGraph 重新实现一遍，
用来对照两种编排方式的差别。

## 跑起来

```bash
npm install
npm run demo
```

三条命令：

| 命令 | 跑什么 | 期望停止原因 |
|---|---|---|
| `npm run demo` | 聚焦取证：对规范 → 读目标文件 → 看时间线 → 读决议 → 收尾 | `completed`（2 次读取） |
| `npm run demo:budget` | 贪心乱读：把读取次数花在定不了事的文件上 | `extract_budget`（3 次读满） |
| `npm test` | 7 条测试，四种停止原因各一条 + 减法评测 | 全绿 |

接真模型（任何 OpenAI 兼容网关，让模型自己挑读哪几份）：

```bash
MODEL_BASE_URL=... MODEL_API_KEY=... MODEL_NAME=... npm run demo:real
```

## 图长什么样

```
  START → agent ─(有工具调用)→ tools ─(预算没到)→ agent
            │                     └─(预算到了)──→ decide → END
            └─(没有工具调用)────────────────────→ decide → END
```

**循环就是 `agent ⇄ tools` 这条边。** 问模型 → 它要工具就执行、把结果塞回上下文 → 再问 →
直到它不再要工具。剩下的都是预算、轨迹和边界。

## 三条边界

1. **只取证，不判阶段。** 循环结束后把凑齐的事实交给 `decide` 节点，判断权只有一个出口。
   不这么做的话系统里会出现第二个判据来源——上一版架构失败正是判断权跑到了覆盖面最窄的
   组件手里。测试 `agent 不判阶段` 钉住这一条。
2. **只读不写。** 五个工具里没有任何写操作。归档必须走人工确认的正常流程。
3. **预算是硬的。** 12 轮 / 3 次读取 / 90 秒，任一触顶立刻收敛，并要求模型说清
   **还缺一份记载什么的文件**——"证据不足"是废话，那句话才是能派活给人的信息。

## 五个工具：四个便宜、一个贵

| 工具 | 开销 |
|---|---|
| `list_project_documents` | 免费 |
| `read_document_facts` | 免费（只取已存事实） |
| `get_project_timeline` | 免费 |
| `match_naming_spec` | 免费 |
| `extract_document_facts` | **贵**：读一份扫描件要一次视觉模型调用 |

**agent 真正在做的决策就是"这份值不值得读"。** 上不封顶的话，第一版一定会出现读了 15 份、
花两分钟、结论和读 2 份时一样的情况。`npm run demo:budget` 演的就是读错文件的下场。

工具描述里写清"什么时候用"，不只写"是什么"；但**不许出现任何业务结论**
（"章程通常属于投资实施"之类）——那等于把删掉的关键词表用自然语言种回去。

## 为什么执行工具的节点是自己写的，没用 ToolNode

**ToolNode 不管预算。** 而"这份值不值得读"是这条链路唯一在做的决策，预算判定必须和工具
执行在同一个地方——触顶时才能就地把收尾提示追加进上下文，而不是把模型硬切断。

预算闸门有两道，故意重复：图层一道（追加收尾提示），工具层一道（第 4 次调用直接拒绝）。
理由是实测教训：**凡是"禁止模型做某事"的约束，都不能只写在指令里。**

## 关于那个"脚本模型"

默认跑的不是真模型，是个确定性的动作序列。**它不是在假装智能，它是个测试替身。**
图的结构、工具执行、预算判定、停止原因分类全都真的在跑，只有"下一步选哪个工具"被固定了
——这样每次跑结果一样，循环逻辑本身才测得准。要看真模型自己挑文件，跑 `--model=gateway`。

生产代码里同样的接缝叫 `DeepenDeps`（模型网关 / 档案存储 / 判定器三个都可注入）。
不留这个接缝，这段逻辑就只能靠联网跑真实文件来验，太贵也太慢。

## 数据

`src/fixture.ts` 里是一个 8 份文件的项目，形态照搬真实客户项目里那对公司章程：
两份同名同类型的章程，**单看任何一份都判不出阶段**，必须拿全项目的注册资本数字去比对
（1173.624 万 → 1304.027 万）。公司名和金额已改写，客户原件不进版本库。

关键设计：**扫描件的内容放在 `hiddenFacts` 里，不调 `extract_document_facts` 就看不到。**
和线上"没 OCR 过就只有文件名"完全一致——否则 agent 的取证决策没有意义。

## 判定器里没有"文档类型 → 阶段"映射表

只有两条**依据**（不是结论）：

1. **数值链**：本文件记载的数值，等于某份文件记载的"变更前值"还是"变更后值"。
2. **日期链**：本文件的落款日在那次变更之前还是之后。

换任何项目、任何文件类型这两条都成立。这就是上一版架构留下的教训：
**人工知识要写成"依据"，不要写成"结论"。** "缴款通知书 → 投资实施 45 分"是结论，
换个没写过的类型就失效；"文件记载的资本与交易文件的变更后值一致 → 交易完成后形成"是依据。

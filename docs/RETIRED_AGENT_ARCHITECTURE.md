状态：**已于 2026-08-04 删除**，本文保留其完整逻辑供日后参考。
替代方案见 `CLASSIFICATION_REDESIGN_PLAN.md` 与 `src/lib/classification/minimal/`。

这套架构在君柔项目 35 份真实文件上运行过，有实测数据。它不是失败品——里面的
章程比对逻辑至今仍是正确的，只是被放在了错误的位置（当裁判而不是当校验）。
下线的原因是覆盖面，不是正确性。

## 2. 关键词表（`business-stage.ts`）

判断的实际主导者。把文件名、正文、事实摘要拼成一段文字，用 40 个词做子串匹配累加分。

### 阈值

```
MIN_STAGE_SCORE = 50   第一名至少 50 分
MIN_STAGE_GAP   = 15   第一名比第二名至少高 15 分
```

两条都过才算 `decided`；低于 50 叫 `insufficient`，差距不足 15 叫 `conflict`，都转人工。

### 完整词表

| 阶段 | 词（权重） |
|---|---|
| pre_initiation 立项前 | 立项前 60、保密协议 35、nda 35 |
| initiation 项目立项 | 项目立项 60、立项会议 50、立项会 50、立项申请 50、立项报告 50、同意立项 45、不同意立项 45、通过立项 45、立项表决 45、立项 25 |
| due_diligence 尽职调查 | 尽职调查 60、尽调报告 50、业务尽调 45、财务尽调 45、法律尽调 45 |
| investment_decision 投资决策 | 投资决策委员会 60、投委会决议 55、投资决策 50、上会申请 45、同意投资 45 |
| investment_execution 投资实施 | 投资实施 60、增资协议 45、交割确认 45、缴款通知 45、工商变更 40 |
| post_investment 投后管理 | 投后管理 60、投后报告 50、投后风险 45、实地调研 40 |
| exit_decision 退出决策 | 退出决策 60、退出投委会 55、退出表决 50、退出方案 45 |
| exit_execution 退出执行 | 退出执行 60、退出交割 50、退出价款 45、档案移交 40 |

注意增资协议 / 交割确认 / 缴款通知都是 **45**，刻意卡在 50 分线下——让文件名单独
决定不了它们，必须配合事实抽取。这是有意的设计。

### 文档类型阶段先验（+55）

只给"在当前目录体系中不存在跨阶段歧义"的类型：

```
confidentiality_agreement        → pre_initiation
project_initiation_application   → initiation
project_initiation_report        → initiation
business_plan                    → initiation
due_diligence_report             → due_diligence
investment_recommendation        → investment_decision
investment_compliance_review     → investment_decision
capital_increase_agreement       → investment_execution
shareholder_agreement            → investment_execution
closing_confirmation             → investment_execution
payment_notice                   → investment_execution
```

公司章程、营业执照、财务报表**刻意不在表内**——它们跨阶段出现。

### 其他加分来源

| 来源 | 分值 |
|---|---|
| 关键词表 | 无上限，实测 50–75 |
| 文档类型先验 | +55（覆盖 11 种类型） |
| 项目时间线事件直接引用本文件 | +70 |
| 关联文件旁证 | **+20 封顶** |

### 实测覆盖面

35 份真实文件，只用文件名：**命中 8，判错 0，无结论 27**。

高精度、低召回——本质是"文件标题里直接写了阶段名"的检测器。沉默的 27 份包括
股东协议、加入协议、出资证明书、电子回单、公司章程、股东会决议、营业执照、
投资建议书、专家委员会表决结果、Teaser、以及全部 8 份财务报表。

## 3. 逐类比对规则（`context-decision.ts`）

只有 5 种文档类型有专属打分器，其余走 `scoreGenericDocument`（完全依赖关键词表，
关键词说不出话就直接 `insufficient`）。

### 公司章程消歧（最有价值的部分）

两个候选各起步 20 分：

| 证据 | 加分 |
|---|---|
| 事实里出现"增资后""新增股东""增加至""本次增资" | 投资实施 +35，同时给投资决策记 20 分反证 |
| 出现"交易前""增资前""投前""原股东""上会材料" | 投资决策 +35，给投资实施记 15 分反证 |
| 记录了注册资本前后变化或股东结构变动 | 投资实施 +25 |
| 时间线事件点名了本文件 | 按该事件的阶段 +30 |
| 章程日期 ≥ 股东会批准日期 | 投资实施 +15；早于则投资决策 +15 |
| **关联章程注册资本更高/更低** | **±30 —— 见下方缺陷** |
| 匹配关联交易文件的变更前/后值 | ±30 |
| 项目已有投资实施事件 | 投资实施 +5（证据文案明写"弱先验，不能单独决定历史文件阶段"） |

### 已知缺陷：比大小那 30 分

```
if (higher) addEvidence(decision, 30, '关联章程注册资本更高，当前文件更可能是交易前版本');
if (lower)  addEvidence(execution, 30, '关联章程注册资本更低，当前文件更可能是增资后版本');
```

证据文案里写死了"增资后"。**注册资本并非单调递增**——减资、股权回购、对赌退出都会
让它减少；2024 年新公司法要求五年实缴，2025–2026 年大量公司主动减资。

在君柔项目里被其他信号掩盖了，但项目里还没归档交易文件时它是唯一的资本信号——
**那时遇上减资就直接判反**。这是替代方案彻底放弃"比大小"的直接原因。

### 强制人工复核（无论分数多高）

- 事实抽取完整度 < 60
- 事实仅来自文件名（`sourceQuality === 'filename_only'`）
- 文档类型是 `investment_compliance_review`

## 4. 那道闸门：`finalizeDecision`

**这是整套架构的核心问题所在。**

```
if (stageDecision.selectedStage) {
  候选 = 候选.filter(阶段 === selectedStage)
  if (一个都不剩) {
    候选 = [该阶段文件夹]   // 直接覆盖掉前面所有精细打分
  }
}
```

翻译：**关键词表算出的阶段对 5 类精细比对规则拥有一票否决权。** 章程比对那套认真写的
逻辑，只要和关键词表结论不一致，整个被推翻。

实测记录：一份股东会决议被关键词表锁定为 `due_diligence`，界面上的证据原文是

> ✓ 业务阶段已锁定为 due_diligence
> ✓ 上下文候选与已确认阶段冲突，按阶段文件夹作为最终归档位置

正确答案是投资实施，被闸门推翻了。

反方向同样致命：关键词说不出阶段时，无专属打分器的文档直接 `insufficient` +
`requiresHumanReview` + `confidence: 0`。**35 份里 27 份走这条路。**

## 5. LangGraph Agent（`classification-agent.ts`）

5 个节点，`GRAPH_VERSION = 'classification-agent-langgraph-v2'`：

```
START → plan_evidence ─┬→ retrieve_related_document → context_decision ─┬→ complete → END
                       └────────────────────────────→                   └→ human_review → END
                                    ↑                                          ↑
                              （可循环回 plan_evidence，最多 maxRounds 轮）
```

### 每个节点做什么

**plan_evidence** — 按文档类型查一张"取证计划表"（`RELATED_TYPE_PLANS`），得出该找哪些
类型的关联文件。表只覆盖少数几类；不在表里的拿到通用清单。

**retrieve_related_document** — 从项目已归档文件中挑一份最相关的。**这是整个 Agent 最有
价值的部分，已搬进替代方案**：

| 条件 | 加分 |
|---|---|
| 项目上下文明确记载两文件有关系 | +120 |
| 同一事件同时引用两个文件 | +100 |
| 正是取证清单点名要找的类型 | +60 |
| 与本文件同类型 | +40 |
| 出现相同主体 | 每个 +10，最多 30 |
| 改动了同一字段 | +20 |

取最高分那份放入参考材料，`rounds + 1`，回到 plan_evidence。

**context_decision** — 调 `decideWithProjectContext`，即第 3 节那套规则。

**complete / human_review** — 终止节点。路由条件：`decided` 且不需人工复核 → complete；
否则若还有可拉的关联文件且未超轮次 → 回 plan_evidence；再否则 → human_review。

### 参数

- `maxRounds` 默认 3，clamp 到 1–10
- `recursionLimit: 30`
- **`llmCallCount` 初始化为 0，五个节点都不碰它，原样返回**

界面上那行「Agent 调度 LLM：0 次」看起来像测量结果，实际是恒为 0 的常量。这是
"分不清谁在工作"的直接来源。

## 6. 项目上下文综合（`project-context-synthesizer.ts`，906 行）

调模型把全项目文件事实综合成结构化 Context：事件时间线、阶段假设、文档关系、冲突、
待解问题。`project-context-synthesizer-v3` 对输出加了明确体积上限（事件 8、关系 8、
冲突 5、待解问题 3、标题 30 字、说明 70 字）。

首次响应无法通过 Schema 校验时，自动移除上一版 Context、用更低温度和无缩进紧凑 JSON
再调一次；两次都失败才切换为规则 Context。

### 为什么被删

在两次章程实测中，它贡献的决定性证据是零。真正判对靠的是关联文件事实里的具体数字。
它最有用的那部分信息（章程日期 vs 股东会批准日期）**在股东会决议自己的事实里就有**，
不需要先综合成项目级时间线。

而它最"自信"的那个产出——`latestEvidencedStage`（项目最晚有证据的阶段）——**是有害的**：
它对项目里每份文件都给出同样的答案，不携带区分单份文件的信息。君柔 35 份文件里只有
12 份真属于投资实施，其余 23 份会被它拽错。实测中模型确实拿它当正面证据用了。

替代方案里时间线由代码按日期排序拼出，零模型调用。

## 7. 项目记忆（`session-project-memory.ts` 1147 行 + `durable-project-memory.ts` 762 行）

持久化到 Coze S3，`MEMORY_ROOT = 'agent-memory/v1/projects'`，路径按 projectId 的
sha256 哈希分片。

存储内容：
```
DurableDocumentRecord {
  sourcePath, archivedFileId, facts, agentDecision, firstSeenAt, updatedAt
}
DurableProjectSnapshot {
  projectId, context, contextState, documents: Map, rebuildHistory, revision
}
```

机制：逻辑快照 + 轻量 revision 对象；S3 上传会给 key 追加随机后缀，所以读取时列出
前缀下全部对象、取 `snapshotUpdatedAt` 最新的一个，再清掉旧的。带乐观并发控制和
per-project 锁。

**重判机制**：项目 Context 变化时，回头对已归档文件重新跑 `runClassificationAgent`，
结论变了就在界面上提示。每份重判都要完整跑一遍 Agent。

### 为什么被删

产品定位是初筛、不取代人工审核。版本号、快照生命周期、重建历史服务的是"增量重建 +
多端一致性"，这个场景用不到。

重判本身的方向是对的——**最早上传的文件是在项目知识最少时判的，最可能判错**。但它
在旧架构里跑不起来（每次要跑 Agent）。替代方案把重判改成纯代码校验，成本归零，于是
可以每次归档后全量重跑。

## 8. 两份评测报告的问题

`output/reports/` 里的 6/6 命中率**证明不了任何事**。

评测脚本喂给系统的文件标识是带目录前缀的 `relativePath`，例如
`投资决策/公司章程.pdf`。而目录名就是答案。实测：只把路径字符串丢进关键词表、
不给任何文档事实——

```
★ 路径直接给出正确答案   50分   投资决策/公司章程.pdf
★ 路径直接给出正确答案   60分   投资实施/6君柔科技-公司章程.pdf
★ 路径直接给出正确答案   60分   投资实施/7君柔科技-股东会决议.pdf
★ 路径直接给出正确答案  100分   投资实施/5中山致远望睿交割确认函.pdf
★ 路径直接给出正确答案  100分   投资实施/8中山致远望睿缴款通知书.pdf
· 路径没泄露              0分   中山火炬电子产业基金管理有限公司-君柔科技.pdf
```

**6 个案例里 5 个，光读路径就能答对。** 评测在结构上无法区分"系统真会判"和"系统在读
路径"。此外项目上下文 fixture 是手写的（没有 `synthesizerVersion` / `generatedAt`），
等于把最难的一环替系统做掉了再考剩下的。

界面上拖整个文件夹上传时也有同样问题：`webkitRelativePath` 带父目录名，而
「立项前」「项目立项」「尽职调查」「投资实施」四个目录名本身就是关键词表里的
60 分词。

## 11. 三条教训

**一、让不完整的东西只做加法，永远不要让它挡路。**
判据：少写一条规则，后果应该是"少一次优化"，而不是"这份文件判不出来"。关键词表
覆盖 8/35 却卡在必经之路上，是这套架构最大的结构性错误。

**二、人工知识要写成"依据"，不要写成"结论"。**
"缴款通知书 → 投资实施 45 分"是结论，换个没写过的类型就失效；"文件记载的资本与
交易文件的变更后值一致 → 交易完成后形成"是依据，对任何项目任何文件都成立。

**三、凡是"禁止模型做某事"的约束，都不能只写在指令里。**
实测两次证明：只在 prompt 里禁止模型使用项目整体进度，它完全无视——因为那个信号
大多数时候确实"对"。必须在代码里兜住。
